现在这些具体 bug，其实可以收敛成 5 类框架级问题。我觉得以后汇报也可以按这个讲，而不是按 Redis、selector、symlink、timeout 一条条讲。
1. 执行环境没有完全“标准化”
这一类包括：
- cwd / mount / /app / /framework 不一致；
- pytest、Jest、ospec、Go 各自执行方式不同；
- Node 依赖、Redis、loader、timeout；
- selector 在不同执行阶段解析方式不同；
- Prepare 能跑，不代表 candidate replay 能跑。
它们表面上是 Docker、runner、路径问题，宏观本质是：
同一个任务在不同阶段没有共享唯一的“怎么运行它”的定义。
所以现在引入 ExecutionSpec 的真正意义就是：
任务
 ↓
唯一 Execution Contract
 ↓
所有 replay / QA / package 都使用它
这一类可以叫：
Execution Contract Fragmentation
执行契约碎片化。

---
2. 数据、路径、产物之间的“身份边界”不清楚
这类问题包括：
- raw selector 和 resolved selector 混用；
- source path 和 container path 混用；
- construction workspace 和 final artifact 混用；
- symlink 被展开；
- node_modules / tmp / cache 被带进 verifier；
- historical test patch 被带进 final package；
- fixture 到底属于源码、测试还是临时依赖不明确。
本质上是框架过去没有非常严格地区分：
原始证据
↓
标准化证据
↓
构造过程临时文件
↓
Verifier 产物
↓
最终 benchmark package
因此很多错误实际上不是 verifier 写错，而是：
东西从一个阶段流到下一个阶段时，身份变了，但框架没有明确描述这个变化。
这一类可以叫：
Artifact & Provenance Boundary
产物边界和来源追踪问题。

---
3. Pipeline 还不完全是一个“可靠状态机”
这一类包括：
- 中断之后不知道从哪里恢复；
- repair packet 丢失；
- old evidence 污染新 contract；
- 多 controller 写同一个 attempt；
- candidate 已经生成但 sentinel 不完整就被丢掉；
- infrastructure timeout 被误认为 semantic failure；
- Judge timeout 又触发重新生成 verifier。
本质不是某个 agent 不聪明，而是：
系统还没有完全定义“什么状态下发生了什么、下一步应该去哪、哪些证据还能继续使用”。
也就是说，早期架构更像：
脚本 A
→ Agent B
→ 脚本 C
→ Agent D
现在需要真正变成：
STATE
+
EVIDENCE
+
CONTRACT VERSION
+
TRANSITION RULE
这一类可以叫：
Control & Evidence Lifecycle
控制流和证据生命周期问题。

---
4. Verifier 本身还存在“测 Gold，而不是测功能”的风险
这是最核心的研究问题。
包括：
- private helper binding；
- historical F2P binding；
- interface binding；
- mock DOM 不完整；
- fixture 只支持 Gold object shape；
- transpiler/runtime shim 只支持 Gold 写法；
- candidate 明明语义正确，但在 assertion 前就挂了。
本质上是：
我们声称：
Verifier ≈ Task Semantics

但实际可能是：
Verifier ≈ Historical Test + Gold Assumptions
这就是你们整个项目真正需要解决的东西。
所以这类不是普通工程 bug，而是：
Semantic Validity / Acceptance Breadth
verifier 的语义有效性和多解容忍度。
DeepSWE 真正重要的就是这一点：verifier 应该通过 public API / observable behavior 来判功能，而不是要求实现匹配 reference shape。

---
5. 框架仍存在从“通用系统”退化成“pilot 特例集合”的风险
这是最近越来越值得警惕的一类。
例如：
遇到 NodeBB
→ 加 Redis 特判

遇到 Tutanota
→ 加 DOM 特判

遇到 TS
→ 加 tsx 特判

遇到某种文件
→ 加 functional_* 命名规则

遇到 copytree 问题
→ 再加一个 blacklist
每一个修改单独看可能都合理，但如果这样累积下去，最后框架可能变成：
“能处理我们跑过的那些任务”
而不是：
“能处理一类新的 SWE-Pro → functional verifier 转换任务”。
所以现在一个很重要的架构原则是：
instance 暴露问题
        ↓
识别缺失的 abstraction
        ↓
增加通用能力
而不是：
instance 出错
        ↓
增加 instance workaround
这一类可以叫：
Over-specialization / Generalization Risk
框架过拟合与泛化风险。

---




结合**实际架构**和刚做完的审计

> **保留现在“Prepare → Converter → QA → Package”的主骨架，把目前暴露出来的隐式契约、旁路和 QA 边界收紧。**

当前审计其实已经说明：核心执行链已经成型，但 `ExecutionSpec`、selector、Positive QA、artifact、package 等还有多个旁路；目前最主要的问题不是缺模块，而是**同一件事存在两三套实现或隐式规则**。

# 2. 现在的问题宏观上可以归成 5 类

## A. Execution Contract 还没有真正统一

这是目前最明显的**工程层问题**。

虽然已经有 `ExecutionSpec`，但审计发现：

* Prepare preflight 还会自行拼 runner command；
* service 没完全建模；
* timeout 分散；
* result parsing 没完全统一；
* `/app`、`/framework`、`/tests` 等路径还散落在不同阶段；
* selector normalization 也还有旁路。

所以现在是：

```text
已经有统一契约
但还有很多代码绕过统一契约
```

### 本质

> 同一个 instance 在 Prepare、Hard Validator、QA、Package 中，“怎么运行”还不完全是同一套事实。

---

## B. Artifact Contract 仍然太隐式

现在 verifier 是通过很多隐式规则识别的，比如：

```text
functional_*
functional_f2p.*
顶层 *.py/*.js/*.go
run.sh
```

workspace 又是：

```text
先允许 Agent 生成任意东西
→ 再 blacklist 删除 node_modules/tmp/cache...
```

审计把这两个都明确标成了 regression risk。

### 本质

> 框架还没有非常明确地回答：“Converter 最终到底提交了哪些正式 artifact？”

这会导致：

* 临时文件污染；
* 文件名前缀变成隐式协议；
* package 再次扫描猜测；
* verifier source 和 wrapper 边界不清。

---

## C. Semantic QA 方向已经对了，但闭环还没被真正证明

你现在 Positive / Negative 的基本思想是正确的。

Positive：

```text
合理不同实现
→ Judge 判断 VALID
→ verifier 应 PASS
```

Negative：

```text
从 valid implementation 出发
→ 只破坏一个 behavior
→ Judge 判断 INVALID
→ verifier 应 FAIL
```

而且当前代码已经允许：

```text
P2P PASS
current F2P FAIL
→ 仍进入 Solution Judge
→ Judge VALID
→ VERIFIER_FALSE_NEGATIVE
```

这是正确方向。

问题在于：

> **真实 E2E 还没有证明最新版 Positive QA 状态机真正跑通。**

Tutanota 当前就是旧 attempt，没有真正走完新 contract。

另外 Semantic Judge 的权限边界也还稍显模糊——它应该提供**语义证据**，而不是单独决定 verifier 是否必须 repair。

---

## D. Verifier 本身还可能通过测试环境绑定 Gold

这个是你们最核心的**科研问题**。

最早是：

```text
private helper coupling
internal state coupling
Gold file-layout coupling
```

现在发现更隐蔽的形式：

```text
mock DOM coupling
fixture coupling
runtime shim coupling
transpiler coupling
```

Tutanota 已经提供了比较明确的例子：synthetic DOM 缺失 `querySelector/querySelectorAll`，合理 alternative implementation 可能因为测试环境过窄而不是功能错误而失败。

### 本质

> 不只是 assertion 不能绑定 Gold，**verifier 使用的 mock / fixture / runtime 环境本身也不能偷偷限定实现方式。**

这应该成为 Converter + Semantic Judge 的固定检查项，但不要因为单个实例就硬编码 DOM 特例。

---

## E. Package 仍然重新“猜”历史测试结构

目前 package 通过：

```text
resolved P2P selectors
→ original_test.patch
→ 判断哪些 hunk / fixture / setup 保留
```

这已经比以前好很多，但仍然存在：

* hunk heuristic；
* shared fixture heuristic；
* manifest 缺失时 fallback 扫描；
* clean smoke 仍然依赖 source image，而没有完整证明最终 environment 构建边界。

### 本质

> 前面已经知道哪些 P2P/fixture 是需要的，但 Package 阶段还在重新解释原始历史 patch。

这会让 package 成为新的复杂度中心。

---

# 3. 基于当前结构，我建议具体改这些地方

不是大改 Pipeline，而是把几个关键 contract 收紧。

---

## ① PREPARE：让 ExecutionSpec 真正成为唯一执行来源

这是第一优先级。

现在：

```text
Prepare
自己有部分 preflight logic

Replay
有 ExecutionSpec

Candidate
有 ExecutionSpec

Package
有 ExecutionSpec
```

应该收敛成：

```text
Prepare
   ↓
生成并冻结 ExecutionSpec
   ↓
之后所有执行
只消费 ExecutionSpec
```

具体要改：

### 把这些全部收进去

```text
runner family
cwd / module root
selector style
loader
container paths
services
timeout
result parser
```

尤其现在：

```text
services = ["redis"]
```

可以先不用设计很复杂的 ServiceAdapter，但至少改成结构化：

```text
service:
  type: redis
  start_command:
  readiness_command:
  timeout:
```

### 统一 container path

最好固定一套：

```text
/app        repo
/verifier   verifier
/framework  framework runner
/logs       execution output
```

不要不同阶段：

```text
/app/verifier
/tests
/framework
/workspace/app
```

同时承担相似语义。

`/workspace` 可以继续用于 mini-swe-agent，但它应该属于 Agent workspace，不属于 replay contract。

---

## ② CONVERTER：保留单 Agent，但输出契约要清晰

不用增加 Semantic Mapper、Builder 等角色。

还是：

```text
一个 Converter
```

但强制它最终只提交几种正式产物：

```text
instruction.md
verifier_manifest.json
verifier source files
fixtures/runtime files
conversion_trace.json
```

### 最重要的一刀

**删除 `functional_*` 作为发现测试的契约。**

现在审计已经明确指出：

```text
_functional_file()
functional_f2p.*
```

仍参与运行和 package discovery。

以后：

```text
文件叫什么
```

不重要。

`verifier_manifest.json` 明确声明：

```text
entrypoints
test_files
fixtures
runner
behavior mapping
```

Hard Validator 和 Package **只读 manifest**。

---

## ③ Converter workspace：从 blacklist 改成明确 output

这个也值得直接改。

现在：

```text
workspace
→ Agent 随便生成
→ 框架过滤
```

改成：

```text
converter workspace/
├── scratch/
└── output/
```

Agent：

```text
scratch/
```

里随便探索。

最终只允许：

```text
output/
```

进入 revision。

再根据 manifest 校验。

这样可以一次性解决很多：

* node_modules；
* tmp；
* symlink；
* cache；
* 临时脚本；
* 实验 package。

不需要继续补 blacklist。

---

## ④ Hard Validator：统一成一套 execution adapter

你已经有 execution adapter，不需要重新设计。

需要做的只是把旁路消掉：

```text
Prepare preflight
Base/Gold
candidate
mutant
package smoke
```

都调用同一套：

```text
run(execution_spec, repo_state, test_target)
```

而不是每个阶段有自己的 runner command。

同时统一 FailureClass。

建议至少分成：

```text
INFRASTRUCTURE
ARTIFACT
VERIFIER_SEMANTIC
CANDIDATE_SEMANTIC
PACKAGE
INTERRUPTED
```

再用 subtype：

```text
RUNNER_MISSING
SERVICE_FAILURE
TIMEOUT
FALSE_NEGATIVE
FALSE_POSITIVE
...
```

这样就不会再出现：

> Converter 报错，但 failure_class 却是 `VERIFIER_SEMANTIC`

这种混乱。当前审计已经发现这一点。

---

# 4. QA：保留 Positive Solver + Negative Mutator，这是必须的

这部分我反而不建议简化掉。

因为：

```text
Base fail + Gold pass
```

只能证明：

> verifier 能区分 Base 和 Gold。

完全不能证明：

> verifier 能接受其他正确实现。

也不能证明：

> verifier 会拒绝那些只满足部分行为的近似实现。

因此：

### Positive Solver

目标是：

```text
找不同于 Gold 的合理实现
```

验证：

> acceptance breadth

### Negative Mutator

从已经确认 valid 的 solution 出发：

```text
只破坏一个 behavior
```

验证：

> rejection strength / coverage

这是 QA 最值得保留的核心设计。

---

## 但 QA 的判定最好统一成四象限

不用继续让状态名越来越复杂。

```text
                 Verifier

              PASS        FAIL

VALID         TP          FALSE NEGATIVE
solution

INVALID       FALSE       TRUE REJECTION
solution      POSITIVE
```

其中：

```text
Judge
→ 判断 VALID / INVALID

Hard replay
→ 判断 PASS / FAIL
```

两者结合后才产生 verifier verdict。

这样 Judge 不会成为最终 grader。

---

## historical F2P 的地位也固定下来

我建议彻底写死：

```text
historical F2P
=
conversion scope
+
intent provenance
+
audit metric
```

它不再参与：

```text
candidate correctness
```

最终判定。

你们目前这部分方向已经基本正确。

---

# 5. Repair：只允许两类回路

这个可以极大简化 controller。

## A. Verifier semantic defect

例如：

```text
VALID candidate + verifier FAIL
INVALID mutant + verifier PASS
Semantic Judge 发现 prompt/verifier overreach
mock coupling
```

走：

```text
Converter REPAIR
→ new revision
→ Sanity
→ Semantic Judge
→ Hard Validator
→ Replay ALL accumulated QA
```

非常关键的是：

> **Repair 后必须 replay 所有旧 Positive / Negative evidence。**

不能只确认刚刚失败的那个。

---

## B. Infrastructure defect

例如：

```text
Docker
mount
runner
service
timeout
image
endpoint
```

走：

```text
framework repair / retry
```

**不产生新的 verifier revision。**

这个边界一定要非常硬。

---

# 6. Package：不要再有新的 verifier discovery

Package 应该越来越“笨”。

输入直接是：

```text
accepted verifier manifest
+
retained P2P
+
required fixtures
+
instruction
+
environment
```

然后机械打包。

不要再：

```text
扫描 functional_*
扫描 *.py/*.js/*.go
```

寻找 verifier。

---

## 对 P2P patch heuristic，我建议先不大改，但做一个约束

不用现在立刻设计 RegressionBundle 大系统。

可以先让 Prepare 在 resolve P2P 时额外输出：

```text
p2p_assets.json
```

记录：

```text
selectors
test files
fixture files
shared support files
```

以后 Package 优先消费这个。

只有确实无法确定的 shared hunk 才 fallback 到当前 heuristic，并显式标记：

```text
AMBIGUOUS
```

这样能逐渐把复杂度从 Package 移回 Prepare，而不需要大重构。

---

# 7. Clean replay 还差最后一步

当前 smoke 已经是 clean Base checkout，这很好。

但是审计发现：

> 它仍直接使用 source image，没有真正验证最终 `environment/Dockerfile` 构造出的环境。

因此 Package 最终最好验证：

```text
final_task/
    environment/
    tests/
    instruction
```

本身能够从头建立 evaluator 环境并完成：

```text
Base FAIL
Gold PASS
P2P PASS
```

这样才能证明：

> final_task 不依赖 construction workspace 的隐藏状态。

---

# 8. Controller 不用重写，只需要瘦身

当前：

```text
state.json
events.jsonl
repair packet
lock
contract version
```

其实已经够了。

不要再设计复杂 DAG engine。

只要保证 Controller 不负责理解：

```text
pytest
Redis
tsx
DOM
selector
```

它只看：

```text
stage result
failure class
revision id
evidence
```

然后决定：

```text
continue
retry
repair
stop
package
```

即可。

---

# 9. 最后可以把当前需要解决的事情分成三个优先级

## 第一优先级：现在就应该改的“架构旁路”

这些是比较明确的问题：

```text
ExecutionSpec 不唯一
functional_* discovery
workspace blacklist
分散 timeout
重复 container path
Prepare 自己拼 runner
failure class 不统一
package fallback 扫 verifier
```

这些都是**确定的框架问题**，不是需要继续实验验证才知道的问题。

---

## 第二优先级：保留机制，但需要真实 E2E 证明

包括：

```text
最新 Positive QA contract
Negative Mutant
repair + accumulated evidence replay
Node / TS / Go execution adapter
service lifecycle
package clean replay
```

目前“代码存在”不等于“闭环成立”。审计也明确指出当前最新版尚未完成 Python/JavaScript/TypeScript/Go 的 fresh Docker cross-validation。

所以这部分**先别继续设计**，应该靠 fresh tasks 去验证。

---

## 第三优先级：目前不要急着泛化

例如：

```text
Tutanota transpiler/runtime shim coupling
```

DOM mock 缺少标准 API 已经有实际证据。

但更广义的：

> “所有 transpiler/runtime shim 都是框架问题”

目前证据还不够，审计也明确指出这一点。

所以：

```text
记录 taxonomy
加入 Judge checklist
继续通过实例收集证据
```

暂时不要因此设计很重的通用 runtime framework。

# 最后总结成一句架构调整原则

你们现在不用重新造一个 VerifierTrans。

保持：

```text
Prepare
→ Converter
→ Verifier QA
→ Package
```

这四块就够了。

现在真正要做的是把里面的隐式契约收紧：

```text
Prepare
→ 唯一 ExecutionSpec

Converter
→ Manifest 驱动 artifact，而不是 functional_* / blacklist

Validator
→ 唯一 execution adapter + 统一 failure classification

QA
→ Solver Positive + Mutant Negative
→ Judge 判断语义，Replay 判断 verifier
→ false positive / false negative 才触发 Converter repair

Package
→ 消费明确 artifact，不重新猜 verifier 和 historical test
→ final clean replay
```
