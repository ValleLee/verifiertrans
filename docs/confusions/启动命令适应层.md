Docker 只保证“在一个固定环境里执行”，不会自动把不同语言的执行方式统一起来。

可以分成三层：

```text
Docker image
  ├─ 操作系统
  ├─ Node/Python/Go runtime
  ├─ 已安装依赖
  └─ 项目源码

Execution adapter
  ├─ 用什么命令启动
  ├─ 如何加载测试文件
  ├─ 如何解释 selector
  └─ 如何收集退出码

Verifier artifact
  └─ Converter 生成的具体测试代码
```

例如同样在 Docker 里：

```bash
node /app/verifier/functional_f2p.js
python3 /app/verifier/functional_f2p.py
go test /app/verifier/functional_f2p.go
```

Docker 只提供这些命令可能存在的环境；真正执行哪个命令，是 execution adapter 决定的。

TypeScript 就更明显：

```bash
node functional_f2p.ts
```

这不一定能运行，因为镜像可能只有 Node，没有：

- TypeScript 编译器；
- ts-node；
- tsx；
- Node 的 TypeScript loader；
- 正确的 Mocha/Jest/Vitest 配置。

所以“在 Docker 中”不等于“任何语言都能直接运行”。Docker 解决的是环境隔离，execution adapter 解决的是语言和测试框架的启动协议。

同理，NodeBB 使用 JavaScript + Mocha 时可以是：

```text
Docker image
  → Node runtime + node_modules
  → execution adapter 启动 Mocha
  → framework runner 根据 selector 运行测试
```

但另一个 TypeScript + Vitest 项目可能需要：

```text
Docker image
  → Node + TypeScript loader + Vitest
  → execution adapter 启动 Vitest
  → framework runner 用 Vitest 的方式筛选测试
```

两者都在 Docker 中，但启动命令、模块加载方式、selector 语义和结果格式都不同。

因此我们才需要 execution adapter。它不是为了替代 Docker，而是告诉 Docker：

> 在这个镜像里，针对这个项目，应该用什么确定性的方式运行 verifier 和原生测试。

目前框架已经把这层抽出来了，但 Node adapter 实际主要覆盖 JavaScript/Mocha；TypeScript、Jest、Vitest 还需要补充 runner discovery 和 preflight。
